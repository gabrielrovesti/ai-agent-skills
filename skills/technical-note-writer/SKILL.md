# Technical Note Writer

Use this skill when the real task is not only finding the answer, but packaging it so another person can use it immediately.

## When to use

- Internal notes
- Support or stakeholder replies
- Colleague-ready technical explanations
- Short implementation status updates
- Self-contained analysis artifacts

## Default approach

1. Decide the audience:
   - technical peer
   - support/stakeholder
   - future self
2. Decide the purpose:
   - diagnosis
   - decision
   - implementation status
   - blocker clarification
3. Compress the output around what the reader needs to do next.

## Structure options

### Diagnosis note

- question
- verified facts
- conclusion
- practical next action

### Implementation status

- what is already implemented
- what was verified
- what is still blocked
- what is needed from others

### Support reply

- direct answer to the user's question
- short reason in plain language
- operational next step if relevant

## Writing rules

- Prefer short, natural prose over heavy technical dump.
- Lead with the conclusion when the audience needs a quick answer.
- Keep internal fallback mechanics out of external-facing wording unless explicitly requested.
- Separate facts from assumptions.
- If a constraint changes the outcome, state it explicitly.
- If evidence is partial, say so without hedging the core verified point.

## Quality bar

The note should stand on its own without requiring the chat history to decode it.
